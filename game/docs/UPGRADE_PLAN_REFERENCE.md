# 01 结论与升级方向
先补完整体验，再增加内容数量

建议继续沿用现有共享模拟核心，不推倒重来。当前版本已经具有经济、建造、战斗、迷雾、AI、存档、操作快捷键以及服务端权威联机基础。真正限制完成度的，是开局公平性、原作特殊机制的深度、地图重复、界面分层，以及公网服务交付缺口。[S01–S08]

| 决策 | 建议与理由 |
| --- | --- |
| 优先级一：能公平、稳定地玩 | 先修出生点、资源配置、无敌方开局；建立完整回归和断线恢复。 |
| 优先级二：能做出战术选择 | 补地图、侦察、骚扰、扩张和各阵营招牌机制，避免只拼坦克数量。 |
| 优先级三：一眼看懂、一按就对 | 分离主页、设置页和房间页，补单位差异化图标、反馈、教程。 |
| 优先级四：交付真实的联机服务 | 国内公网入口、房间目录、权威房间服务器、监控和运维必须一起完成。 |
| 美术推进方式 | 先做三阵营代表单位与建筑的完整样板，再成批替换；不先追求全场高面数。 |

## 产品边界不要再次漂移

内容基线仍是《尤里的复仇》方向：盟军、苏联、尤里三套科技体系；美国、英国、法国、德国、韩国、俄罗斯、伊拉克、古巴、利比亚、尤里共十种国家选择。最多八个参与席位，不是“只有八个国家”，也不是“八名玩家之外再无限加 AI”。人类、电脑与关闭席位应独立配置。[S02]

单机与联机共用规则并行迭代。首发优先遭遇战、朋友对战、团队合作与沙盒；完整战役、排位系统和商业化养成不进入当前关键路径。常规对战不加入永久属性成长或付费强度。

# 02 核查结果与测试边界
区分“本次已验证”“代码可见”“尚待真实环境验证”

| 项目 | 核查结果 |
| --- | --- |
| 内容规模 | 128 个单位／建筑定义，其中单位 72、建筑 56；三张地图。定义数不代表完整还原度。 |
| 核心结构 | 自定义 WebGL2；模拟运行于单机 Worker 或 Node 服务端；固定步长 0.1 秒。 |
| 已有表现能力 | 实例化绘制、阴影、程序化模型、位置与朝向平滑均已存在，不能列成从零新增。 |
| 已有操作能力 | 右键拖图、镜头参数、编队／路径点、排队、集结、建造放置、碾压等已有代码及部分测试覆盖。 |
| 已有网络能力 | 建房／加入／准备／开局；服务端控制权校验、迷雾过滤、序号去重、心跳及恢复令牌。 |
| 明显缺少 | 成品化自动重连、公开房间目录、完整席位编辑、聊天、观战、回放及已部署公网服务。 |

## 本次重新运行的结果

npm test 的四组测试合计 90／90 通过：模拟 19、操作 32、网络协议 12、镜头 27。另运行了定向模拟审计与 100／300／600 单位合成基准。[T01、T03、T04]

浏览器冒烟测试记录了 7 项通过，包括离线页面初始化、八席位单机推进、实际造厂造车、存档恢复、暂停，以及 128 类模型生成。后续步骤在本环境超时，整套浏览器测试未完成。另一轮浏览器审计只完成初始化和房主建房。不得据此宣称浏览器端到端测试全部通过。[T02]

> 网络测试使用同机回环地址的独立 WebSocket 客户端；并非两台电脑的真实 LAN，也非八名真人跨网对战。600 秒模拟测试是加速模拟，不是十分钟真实网络稳定性测试。截图中的 FPS 来自软件渲染，不可用来判断 RTX 4060 的帧率。

## 覆盖程度的正确理解

现有测试证明若干关键路径可用，却没有覆盖出生点公平性、同队无敌人、跨运营商时延、断网后界面恢复、攻击者资源耗尽压力和完整原作数值。下一版必须把这些缺口加入测试，而不是把“90 项通过”当作全部体验合格。

# 03 必须先修的四类问题
这些项目比再新增二十个单位更影响对局质量

| 问题／优先级 | 当前证据 | 修复与完成标准 |
| --- | --- | --- |
| P0：出生位置分配 | 两人局使用固定列表前两点 (34,154)、(24,96)，距离约 58.86；四人局也偏向左／上侧。 | 拆分 seatId 与 spawnId；地图明确 2／4／8 人布局，关闭席位不影响分配。镜像同族两人开局对称。 |
| P0：出生矿种不一致 | 0 号附近为普通矿＋宝石，1 号为普通矿＋普通矿；代码按座位奇偶分配宝石。 | 对称出生位采用一致矿种、等效收益与可达距离；交换座位跑经济基准。 |
| P0：无敌方也能开局 | 两个真人设为合作同队后，模拟推进约 2 秒即出现胜者。 | 房间开局前检查至少两个敌对存活阵营；合作模式必须保留敌方 AI／敌对队伍。 |
| P0：公网完成度误判 | 地址输入框和房间代码已经存在，但没有已交付的公网入口与完整服务栈。 | 公网按钮只能连接真实上线端点；无服务时说明状态，不显示虚构在线人数。 |

前三项由定向模拟直接复现。[T03] 矿种差异证明配置不一致，并不等于已经通过大量对局证明某个出生点必胜。公平性应以初始收益、路径、地形与多轮对局共同验收。

## 其次处理的体验风险

三张地图的矿点与中立建筑配置相同，海岸图另有水域差异；不能把环境换色当成三套完整战术地图。迷雾每 0.5 秒更新一次，应验证揭雾、锁定目标与隐形显现是否产生可感知迟滞。客户端收到断线事件后主要给出提示，缺少自动重连和明确的“此时不能下令”状态。[S03、S04、S07]

当前完整 JSON 快照按 10Hz 发送，随着可见单位数增加，带宽和序列化可能先于模拟计算成为瓶颈。先测量再扩容，不能仅凭模拟每步耗时小，就宣称一台小服务器能承载大量八人房。[S08、T04]

> 执行顺序：新增复现测试 → 最小修复 → 90 项原测试回归 → 对应真实场景验收。不要为修公平性而同时重写镜头、渲染和全套 UI。

# 04 当前界面与观感诊断
保留已有军事终端风格，改善信息层级与辨识度

![1280 × 720 当前菜单截图：主视觉占比大，详细部署选项集中在右侧。](evidence/screenshots/current_menu_720.png)

| 观察 | 升级方式 |
| --- | --- |
| 主页与部署表单合在一起 | 首页只做继续、单人、联机、训练、设置；进入模式后再出现完整参数。 |
| 地图主要依靠名称选择 | 加入可辨认的预览、出生点、资源与水陆比例说明，别让地图变成盲选。 |
| 大量同色细线和装饰英文 | 主操作用清晰中文；保留少量装饰文字但弱化；错误、禁用、主按钮层级分明。 |
| 单位／建筑图标风格一致但区分弱 | 按真实模型渲染独立缩略图；同类底色统一、轮廓差异突出，稀有机制加小徽标。 |
| 阵营色大面积覆盖模型 | 区分“阵营材质语言”与“玩家队伍色”；队色主要放肩甲、条带、旗帜和识别灯。 |

画面不需要变成写实战争片。建议走“保留红警比例与剪影的精细风格化三维”：正常战场缩放先能认单位，近看才看到金属分件、履带、炮塔和建筑结构。黑色迷雾应保留策略功能，但边缘、地表明度和模型对比度可以更柔和、清楚。

> 这里是对当前截图和代码的设计评价，不是新界面已经实现的展示。建议在同一张地图、同一镜头和同一光照下做前后对比，避免用不同场景掩盖改进幅度。

# 05 更还原：先建立规则基线
“有这个名字”与“行为接近原作”必须分开管理

现有目录使用了大量原作单位名称，但数值、建造节奏与特殊机制仍有简化，包内也明确声明不是 1.001 完整复刻。[S02、S09] 下一阶段应指定一个可合法使用的原作版本作为对照，建立可追溯的规则表与实机用例，而不是凭印象调整。

| 独立状态维度 | 标记方式 |
| --- | --- |
| 内容收录 | 未收录／已定义；解决“目录里是否存在”。 |
| 生产与科技 | 沙盒可生成／正常可生产／前置、国家限制、建造者与生产线已核对。 |
| 机制与数值 | 占位／基础行为／完整状态机／原作对照验证；分别记录数值来源。 |
| 美术与音效 | 程序模型／样板达标／最终资源；来源、授权与替代方案独立记录。 |
| AI 与联机 | AI 会使用／网络状态完整／迷雾安全／回放一致；不能用单机通过代替。 |

## 将经典规则与便捷规则做成两个预设

经典预设：以核对后的科技、经济、护甲、射程、生产和胜负规则为准。增强预设：允许已有基地开局、额外起始部队、便利指令或挑战规则。房间在标题和加载页明确标识，不把增强规则混称“完全原版”。

目前建造付款、生产线分类、初始基地和兵力、胜负判断都有项目自定实现；应逐项验证。尤其不能把“建筑全部消失就败”或“载具、飞机、舰船共用一条队列”的现状，未经对照就写成原作规则。[S03、S09]

## 数据工程要求

拆出规则数据、单位定义、武器／弹头／护甲矩阵、地图配置和美术引用；为每次发布生成 buildHash、rulesHash、mapHash。房间开局同时比对这些标识，内容不一致就禁止开始并说明哪一项不同。

每个机制采用“场景布置 → 输入命令 → 状态变化 → 可见反馈 → 边界例外 → 网络结果”六步用例。优先验证常用单位的交互，而不是一次批量修改所有 128 个定义后再找回归错误。

> 保留现有 64 节点路径规划、Shift 追加、小地图命令、右键拖图和三种迷雾模式。便捷操作可以现代化，但不得暗中改变房主已锁定的对局信息规则。

# 06 阵营特色：从占位技能变成战术
先补最能让玩家感知差异的机制链

| 体系 | 优先完善 | 玩家应感受到的变化 |
| --- | --- | --- |
| 盟军 | 多功能步兵车乘员武器；幻影伪装表现；超时空攻击过程；光棱武器命中表现；机场补弹与返航。 | 侦察、组合兵种、精确打击和保存高价值单位，而非轻坦换皮。 |
| 苏联 | 磁暴步兵充电；恐怖机器人寄生与维修清除；伊文炸弹状态；飞艇／无畏战舰的真实攻击过程。 | 正面火力与高风险骚扰并存；维修、拆炸弹、拦截成为明确应对。 |
| 尤里 | 独立奴隶采矿与释放；磁电抬升／落地；心控容量、过载和归属恢复；飞碟按目标类型作用。 | 单位控制、经济干扰、地形利用与风险管理，不能只有紫色坦克。 |

这些方向针对包内 KNOWN_DIFFERENCES 的已知简化；精确原作参数与全部例外仍需对照验证，不应把上表视为已完成的机制说明。[S09]

## 三组机制验收样板

样板 A：运输与乘员。建立进入、占位、容量、武器切换、卸载位置、载具销毁、控制权改变的完整状态。UI 显示乘员头像和容量；服务器拒绝远距离瞬移进入；录像能恢复每次乘降。

样板 B：特殊控制。用统一状态系统表达心控、眩晕、寄生、抬升和冻结，但每种状态有独立来源、到期、清除和互斥规则。不要为了实现新效果而误删其他效果。所有权变化后重算选中状态、命令权限、迷雾和目标关系。

样板 C：飞行器。机场容量、起飞、航路、投弹、返航、补弹、机场被毁等行为都要有可见结果。当前固定高度漂浮和简化延迟伤害可保留为低质量占位，但不能作为最终还原标准。

## 国家特色与反制信息

十种国家应在选国页清楚显示“专属内容、适合打法、注意弱点”。逐个检查国家限制和科技要求，不用未经测试的强度评级。单位图鉴加入“擅长对付／不适合对付”的机制解释，先用定性说明，待护甲矩阵核对后再显示精确倍率。

# 07 可玩性的核心：地图与经济
六张战术结构不同的地图，比六张换色地图更有价值

当前三张地图共享主要资源与中立布局，地图选择不足以改变决策。[T03] 建议先做六张中小规模地图，每张至少支持一个明确的人数和队伍配置；不要为了“八人全兼容”牺牲所有两人图的节奏。

| 地图提案 | 主要决策 | 公平性要求 |
| --- | --- | --- |
| 双线矿谷｜2 人 | 主路推进与侧路矿车骚扰；中期选择安全副矿或争夺中矿。 | 镜像主矿收益、矿车距离和第一接敌距离；避免单入口封死。 |
| 工业交叉口｜2–4 人 | 可驻军街区、多个绕行口、中心油井；步兵清楼有价值。 | 驻军点不得单方面覆盖对手出厂口；油井到达时间接近。 |
| 海岸争夺｜4 人 | 陆军守正面，海军提供侧翼与海岸火力；陆路不能被迫放弃。 | 双方海军发展空间可用；海军有目标，陆军也有推进线。 |
| 四角扩张｜4 人混战 | 多条扩张路径、争夺外圈副矿；降低全员挤中间的必然性。 | 出生附近资源等价；外交位置优势与随机出生透明。 |
| 双堡垒｜4–8 人团队 | 前排固守、后排发展、两翼包抄；队友可以补防。 | 队内前后位置可选，双方线路与支援时间成对匹配。 |
| 开放盆地｜6–8 人 | 视野争夺、宽正面与多方向切入，检验大军操作和协同。 | 非单通道堵门；拥堵、远近出生与资源分布需压力验证。 |

## 地图要成为真正的数据资产

配置应包含地形／通行层、出生布局、矿区类型和总量、中立建筑、海陆区、装饰密度、推荐人数、预览图及版本。用 seed 控制可复现的装饰或允许随机项；竞技预设不随机改变出生经济。

桥梁、断桥修复、高低地和坡道放到下一阶段：它们需要通行层、射线／射程、放置合法性、单位高度与破坏状态联动。只摆一段桥模型但单位穿过去，反而比没有桥更破坏体验。

> 建议建立固定时长的镜像经济测试：同阵营、同操作、交换出生位，比较收入、空跑时间与资源可达性。数值阈值由地图类型决定；对称竞技地图应接近一致，非对称挑战图明确标注。

# 08 AI、路径与对局节奏
让不同兵种和不同时机真正有用

当前 AI 主要按固定建筑顺序发展，再生产部队进攻；困难档存在额外资金，进攻目标选择会读取敌方总部位置，而不完全受自身侦察信息约束。[S04] 下一步要先区分“公平 AI”和“明确标注有经济加成的挑战 AI”。

| 升级模块 | 设计与验收 |
| --- | --- |
| 侦察与记忆 | AI 只读自己的可见快照／已发现情报；先探索，再记住上次看到的基地。未侦察不得直接精确追踪敌方移动。 |
| 作战计划 | 至少四类计划：早期骚扰、经济扩张、防守反击、组合推进。开局或局势触发切换，避免固定时间全体冲锋。 |
| 兵种配比 | 根据已发现的空军、装甲、步兵和防御设施调整生产；设观察延迟与预算，不能每帧完美反制。 |
| 经济与抢修 | 矿车危险绕行、修理重点、保电、恢复生产、基地被打后的撤退重建；清楚区分缺钱与卡生产。 |
| 微操难度 | 简单档降低反应和操作频率；普通档规则公平；困难档先提高计划质量，经济加成作为显式选项。 |
| 团队合作 | AI 响应防守／进攻／撤退标记；多人合作仍计入八席位总上限，必须有敌对方。 |

## 最优先的地面部队体验

为混编部队设置目标区域而非同一个精确点；短距离分离、通道预约与卡住重寻路结合，保留确定的碰撞和碾压规则。工厂出口被占应提示“出口受阻”，允许恢复后继续出厂，避免单位叠成一团。

攻击移动、停止、警戒、追击距离、反击和切换目标要有一致规则。路径线、终点旗和命令回执应立即显示；服务器确认前不提前扣血、不擅自判断击杀。路径规划在菜单或失焦后要正确退出，避免误下单。

## 节奏目标是测试假设，不是改写原版承诺

增强遭遇战可先用“数分钟内出现侦察与小规模接触、中期必须选择扩张或科技、后期有终结对局手段”作体验目标。经典预设则由核对后的原作经济与速度自然形成节奏，不为追求快而偷偷强化所有单位。

# 09 美术升级：建立可复制的样板
可读性 → 轮廓 → 动态 → 材质 → 特效

现有自定义渲染器已有实例化、阴影和位置平滑，程序模型覆盖面广。[S05、S06] 不建议先切换引擎再重做全部资产；先确认当前渲染器能稳定承接一批高质量样板，再决定引入 glTF／动画资源或更换渲染层。

| 层级 | 制作规格与目的 |
| --- | --- |
| 第一层：正常缩放识别 | 坦克车体、炮塔、履带、武器与阵营剪影明显不同；同类升级不能只换颜色。 |
| 第二层：结构与功能 | 炮口、炮塔旋转轴、履带接地、建筑入口、出厂口、机场停机位与实际行为对应。 |
| 第三层：材质 | 盟军偏清晰面板与冷色识别，苏联偏厚重装甲和工业结构，尤里偏非对称机械与特殊能量；均可使用任意队伍色。 |
| 第四层：动态 | 步兵待机／走跑／攻击，履带滚动，开火后坐，建筑施工／受损／停电／摧毁。 |
| 第五层：环境 | 地面材质分区、道路边界、水岸过渡、装饰疏密和环境阴影；装饰不得误导通行。 |

## 首批样板：九个对象就能确定整套品质

选择灰熊、犀牛、狂风三个主战载具；三阵营建造场；三种基础步兵。每个对象完整交付模型、材质、队色遮罩、枢轴、碰撞／选框、所需动作、两级以上细节版本、独立图标和许可记录。采用相同场景做并排验收，再扩展到高频生产建筑和招牌单位。

三角面数和贴图预算作为样板实验参数而非最终承诺：普通载具可从约 2,000–8,000 三角形、建筑约 8,000–25,000 起步；重点看同时可见对象数、实例化批次和显存。步兵在常规视角保留完整轮廓，不用细小装备牺牲动作可读性。

## 工程接口

把模型选择、材质参数、炮塔／炮口锚点、血条高度、选框尺寸等移入 artManifest。逻辑只依赖语义锚点，不依赖模型内部临时命名。保留低配程序模型回退；在线资源分块加载，单机发行包仍应可离线启动。

> 不直接提取、打包原版音乐或未知授权模型。公开发布前建立来源台账；非商业用途不是自动获得所有素材使用权，具体边界见第 26 章。

# 10 表现与反馈：战场必须“说清楚”
华丽应服务于判断，而不是挡住单位

| 场景 | 视觉／声音反馈 | 信息边界 |
| --- | --- | --- |
| 建造与生产 | 施工阶段、队列倒计时、完成闪烁、产出门动画；类别专属提示音。 | 进度与服务器状态一致；不能用固定动画假装真实生产完成。 |
| 命中与护甲 | 区分实弹、光束、电流、爆炸和特殊效果；小范围火花与后坐。 | 效果强弱不替代真实伤害；隐藏区域不得凭特效泄漏敌军。 |
| 受损与摧毁 | 受损状态、烟火、残骸和淡出；大爆炸有距离衰减。 | 残骸是否阻挡通行由规则决定，视觉残骸不可造成隐形障碍。 |
| 经济／电力危机 | 缺钱、缺电、矿车受袭、生产停顿有不同图标与可定位通知。 | 同类事件合并与冷却，避免一秒钟播出十条警报。 |
| 选择与指令 | 每阵营确认音，移动／攻击／不可执行图标，鼠标模式明显。 | 先即时反馈意图，后以服务器确认更新实际执行结果。 |
| 超级武器 | 可读预警、目标区域、充能／可释放状态，威胁分级音效。 | 提前透露多少信息属于房间规则，不通过观战或加载页泄漏。 |

## 音频升级的正确顺序

先做选择、命令确认、建造完成、受袭、停电、胜负六类关键反馈，再做每种武器差异和单位语音；最后补背景音乐。当前 WebAudio 合成音可保留为体积小的基础模式，但不应是唯一最终方案。[S07] 所有新录音和音乐采用明确可分发的原创或授权资源。

## 相机：保留 v0.4.0 已经做好的部分

保留右键拖图、滚轮锚点缩放、边缘滚动、灵敏度与惯性设置。继续验证右键“点击下令／长按拖动”的距离和时间阈值，拖过地图后绝不落下一条移动命令；打开菜单、切换窗口或松开指针时必须结束拖拽。

增加镜头预设：经典等角、舒适近景、低配；支持重置镜头、跳到上次警报和编队定位。镜头抖动、闪屏、拖尾、环境粒子都可独立关闭。不要用强烈景深、屏幕污渍和大面积光晕牺牲单位选择。

## 低配不是简单关闭一切

优先降阴影分辨率、远处细节和非关键粒子；保留选框、命令反馈、炮口方向与必要预警。UI 缩放与渲染分辨率分开，让画面低分辨率时文字仍清晰。

# 12 房间界面与在线流程规格
零配置体现在路径与状态，而不只是一个按钮

## 目标玩家路径

启动游戏 → 在线联机 → 创建房间／输入邀请码 → 选择国家与队伍 → 准备 → 开始。玩家无需安装 Node、填写 IP、购买云服务器、改路由器或开端口。实现此前提是开发交付方已经上线兼容服务，而不是把部署说明转交给玩家。

| 房间区域 | 显示与操作规格 |
| --- | --- |
| 顶部状态 | 房间名、可复制代码、地区、当前延迟、隐私状态、版本／规则一致性。 |
| 左侧地图 | 地图预览＋出生点编号；当前席位高亮；点击可选空位，房主可锁定。 |
| 中部席位表 | 昵称、国家、队伍、玩家颜色、出生点、准备、延迟；电脑显示难度，关闭位清晰置灰。 |
| 右侧规则 | 规则预设、起始资金、迷雾、超级武器等；任何影响模拟的更改使所有人取消准备。 |
| 底部互动 | 队内／全体聊天、静音、复制邀请、准备／开局；房主未满足条件时看到具体原因。 |
| 离开与异常 | 离房确认、重新加入、版本不符、满房、房间结束、被移除和服务维护分别说明。 |

## 必须实现的状态机

未连接 → 正在连接 → 校验版本 → 在大厅／房间 → 正在加载 → 对局中 → 暂时断线 → 恢复中／失败 → 结算。每个状态明确允许的按钮、超时策略和回退路径。等待时有真实进度，不能一直旋转却不提供退出。

房间代码由目录服务解析到唯一房间和所属地区。不要让朋友各自“自动选择最低延迟地区”后进入互相不可见的目录；用邀请房间的地区作为加入目标。短代码只是查找工具，不是密码，更不负责 NAT 穿透。

## 首版先让朋友玩得舒服

公开房间、私密邀请码房、最近同玩与再来一局优先于天梯。陌生人匹配以后再做，先记录完成率与离线率。首版不要求绑定社交账号；账户与游客机制须结合运营及合规要求确定，不能以“游客”规避必要义务。

> 联机房主是房间管理者，不等于运行权威模拟的服务器。公网房主关闭浏览器后，对局应继续；LAN 房主关闭整台托管服务器则不能承诺无损继续。

# 13 对战 HUD 与操作升级
尽量保留熟悉的右侧生产栏，但让信息更完整

| 部位 | 改进方案 | 验收重点 |
| --- | --- | --- |
| 资源／电力 | 现金为主，电力供需与停电原因常驻；高级面板可查看收入与支出。 | 不只改变颜色；低电力同时用文字／图标提示。 |
| 生产栏 | 分类独立队列、真实单位缩略图、数量、进度、取消／暂停、快捷键和前置提示。 | 缺钱、缺科技、停电、已达上限、出口被堵必须能区分。 |
| 选择面板 | 按类型分组头像与数量；伤员比例、乘员、经验与特殊状态；点击筛选。 | 选中百个单位时不创建百个昂贵实时预览；异主单位不可操作。 |
| 命令面板 | 仅显示可用命令；不可用时解释原因；危险动作或不可逆操作有明确反馈。 | 技能目标合法性由服务端判定；菜单不吞掉退出键与指针释放。 |
| 小地图 | 攻击／求援标记、镜头框、队友颜色、警报跳转；延续已有小地图下令。 | 不得显示未侦察敌军；文字／形状辅助色盲用户。 |
| 网络状态 | 简洁延迟指示；断线时弹出覆盖条、倒计时与重试，禁止无效下令。 | 恢复后不重复执行已确认命令；不会默默切成单机。 |
| 战场信息 | 适量血条、建造预览、射程／作用区预览、路径节点与编队编号。 | 高亮遵守视野；拥挤战场仍能点选目标。 |

## 操作设计的几个细节

新增空闲矿车／生产建筑定位、同类单位选择、选择伤员、快捷警报定位，以及可重绑定按键。冲突键位必须提示，不默认覆盖既有 Z 路径规划和建筑快捷键。左键／右键两种指令预设要在教程中对应显示。

框选时自动优先作战单位还是包含建筑，应成为清楚的选项；双击同类选择的范围也要有明确规则。按住修理／出售模式时更换鼠标与顶部提示，Esc 必须可靠退出，避免误卖建筑。

## 显示与可访问性

以 1366×768 和 1920×1080 为必测尺寸，覆盖 100%／125%／150% 系统缩放与不同 UI 比例；对战主体页面不产生整页纵向滚动。字号、重要按钮、悬浮说明需可放大；消息记录可回看，重要提示不能只靠声音。

# 14 让玩家愿意再来一局
内容循环围绕策略成长，而不是日常任务

## 低成本、高收益的单机内容

做五个短训练：部署建造场与供电、造厂造兵与集结、侦察和迷雾、矿车保护与维修、组合兵种与特殊单位。每课只有少量明确目标，检测真实行为，失败能直接重试。沙盒增加可保存场景、敌我生成、资金／AI 开关、伤害和状态观察。

| 模式 | 体验目标 | 实现边界 |
| --- | --- | --- |
| 经典遭遇战 | 选择地图与国家，公平开局，以原作规则取胜。 | 不混入永久成长；规则核对完成后再标“经典已验证”。 |
| 快速对战 | 已有基地／缩短准备、合理地图尺寸，减少等候。 | 明确增强预设；不影响经典规则数据。 |
| 双人／多人合作 | 朋友各自运营与协同进攻，AI 有不同打法。 | 总参与席位最多八；4 人＋4 AI、2 人＋2 AI 等明确预设。 |
| 战术挑战 | 护送、守住基地、有限部队突围、反特殊兵种。 | 独立规则和胜负脚本，避免重写常规对战逻辑。 |
| 复盘与再来一局 | 结算后看问题，留在房间换图／换国家／换出生再战。 | 优先胜负解释与关键事件，再做复杂统计图和天梯。 |

## 结算页应该回答三个问题

谁赢了、为什么结束、这局哪里发生了转折。展示队伍和玩家胜负、资源收入、损失价值、击杀、关键建筑被毁与超级武器等事件；统计口径写清楚，避免单看击杀数误导辅助玩家。默认返回原房间，保留队伍和邀请关系。

## 回放与观战的技术底线

服务器记录初始配置、规则／地图版本、随机种子、已接受的命令序列及周期检查点。重放应能定位关键事件；不承诺仅靠随机种子在任意新版本完全重现旧局。遇版本不兼容就提示，或加载匹配的模拟版本。

实时观战必须有权限与延迟策略，玩家离开后不能立即利用全图观战替队友报点。客户端从未收到的隐蔽信息不能由回放预加载泄露；全图历史可在对局结束后按规则开放。

# 15 局域网：从能用到方便用
两种入口，共享同一套模拟和协议

当前 START_LAN.bat 会启动监听服务器，但要求本机已有 Node；同网玩家仍需找到对应地址。[S10] 因此当前属于可用技术原型，不是“发给朋友双击就一定能联机”的成品体验。

| 交付形态 | 推荐流程 | 限制与回退 |
| --- | --- | --- |
| 便携 LAN 启动器｜推荐 | 随包提供已锁版本运行时；点击“创建局域网房间”自动启动服务、打开游戏、显示邀请链接。 | 启动器明确退出与后台驻留；首次系统防火墙授权仍可能需要用户确认。 |
| 纯浏览器加入 | 朋友打开房主提供的本地网页地址；前端与 WebSocket 使用同一 LAN 服务来源。 | 不要求加入者安装 Node；地址／二维码用于分发，不等于自动跨网。 |
| 自动发现｜启动器增强 | 本地辅助进程发现游戏广播／服务通告，UI 展示房间名、人数、延迟、版本。 | 纯网页不承担任意网段扫描；保留复制地址和最近连接。 |
| 高级诊断 | 显示有效网卡地址、服务器端口、同网探测、权限状态；支持多网卡选择。 | AP 隔离、访客网络、公司策略可能阻断；不能让用户关闭全部安全防护。 |

## 兼容性注意

浏览器访问本地网络的权限规则持续变化，Chromium 已推进把 WebSocket 纳入本地网络访问权限控制。[W04] 要验证当前 Chrome、Edge、Firefox 的实际行为；不要指导玩家关闭安全特性，也不要假定公网 HTTPS 页面永远能无提示连接私网 WS。

## LAN 验收步骤

两台不同电脑接入同一路由器，且不依赖互联网；一台在未预装 Node 的干净环境双击开房，另一台打开分享的 LAN 页面加入。验证准备、混合 AI、国家与队伍、地图、开始、下令、胜负与下一局。再测试短断网、多网卡、端口占用和防火墙拒绝后的清楚提示。

加做四人／八人实测；服务器进程持续运行时，某个浏览器离开不应拖死全局。LAN 服务所在电脑休眠或退出程序时则显示会话中断；无迁移机制前，不宣称房主整机掉线仍可无缝继续。

> 目标是“不需要配置开发环境、不需要改路由器”，不是保证所有网络下连一次系统权限确认都不会出现。这样的边界必须在启动器中讲清楚。

# 16 国内公网：应该选什么方案
必须交付正在运行的兼容服务，而不只是服务器教程

本次没有核实到可让上传包直接接入的现成中国公共游戏服务器。本包使用自己的协议和权威模拟逻辑，通用托管平台仍需项目方接入或部署。这不影响玩家端做到无需配置，但不能把开发接入与服务运营的工作省略。

| 方案 | 适配判断 | 本项目建议 |
| --- | --- | --- |
| 项目专用兼容服务，部署在中国大陆云资源上 | 保留 Node 权威模拟；前端内置正式入口，运营方管理域名、证书、房间和资源。 | 首选。最少改动既有核心，但实际部署、费用与维护必须由交付方／运营方承担。 |
| Photon Realtime 中国大陆区 | 官方列上海 cn 区，需为 AppID 申请解锁；20 CCU 免费开发／非商业额度，付费方案另受限制。[W01] | 备选。需要 SDK／协议及服务端逻辑方案适配，不是往原地址框粘贴一个域名。 |
| Colyseus 或成熟 WebSocket 服务框架 | 是房间与服务部署的技术基础，不等于已有本项目可用的公共房间。[W02] | 可替换薄弱的网络层；先做迁移试验，不必为了框架重写 Sim。 |
| CnCNet 等既有红警社区服务 | 服务对象与客户端协议有明确范围；未验证支持这个自定义网页项目。[W03] | 不可假定通用兼容，更不能把其地址当现成公网后端。 |
| 免费 STUN、随机公共中继、内网穿透 | 不是完整游戏大厅、权限校验与权威战斗服务器。 | 不作为正式默认方案；不向玩家转嫁不可靠的第三方配置。 |

## “无需我做额外事情”落实为交付标准

最终交付方提供：已上线服务、有效 HTTPS／WSS 入口、客户端内置配置、真实多人测试结果、服务状态页、故障处理方式和明确的运行期限／费用承担者。玩家只负责进入游戏和选房间。若尚无运营主体或资源授权，这一项应标记“未交付”，不能用占位地址充数。

## 大陆节点与地域命名

大陆、香港与境外节点分开展示，不用“亚洲服务器”模糊宣传为大陆节点。节点位置不等于所有中国玩家都低延迟；最终必须用电信、联通、移动等实际网络验证。邀请加入应跟随房间路由，不能把朋友自动分散到不同地区。

# 17 推荐网络架构
保持服务端权威，逐步替换原型网络层

| 层 | 职责 | 边界 |
| --- | --- | --- |
| 客户端：浏览器／便携壳 | 输入、渲染、声音、UI、可见状态缓存与断线交互。 | 不决定金钱、伤害、命中、视野或胜负；不携带云管理密钥。 |
| HTTPS／WSS 入口 | 正式域名、TLS、静态资源、连接限流、版本配置与路由。 | 主要通过 443 端口对外；不让玩家配置自定义端口。 |
| 大厅／目录服务 | 会话身份、房间列表、短代码解析、准备状态与节点容量。 | 目录一致；不在每帧处理战斗数据，不伪造房间状态。 |
| 权威房间进程／工作线程 | 共享 Sim、固定步长、命令验证、视野过滤、事件和增量状态。 | 按房间隔离；满载时拒绝新房，不把全部房间拖慢。 |
| 持久化与运行支持 | 规则包、地图、结果、回放、必要检查点、日志、告警。 | 不把全部单位状态每帧写数据库；敏感凭据只在服务端。 |

## 先做小而完整的单区域服务

首个公开试运营版本采用一个大陆区域、受控房间数量、完整可观测性。确认每房资源上限和稳定性后，再加更多节点。跨节点扩展需要房间目录、节点归属与路由，不能只多起几个进程就认为房间能互相发现。

## 当前代码的最小迁移路线

继续复用 web/src/sim.js 与规则数据；抽出传输适配器、会话、房间管理、序列化和校验模块。服务端手写 WebSocket 帧处理改用维护中的实现，并锁版本、加依赖审计；原有控制权校验、去重、迷雾过滤和测试保留。[S03、S08]

本地单机仍走 Worker，LAN 与公网走一致网络命令接口。不要因为联网而让单机必须登录服务器；公开网页可分包加载资源，但离线发行版保留自足资源。便携窗口不是独立引擎，应继续验证浏览器输入和 WebGL 行为。

## 上线与升级机制

只把新房间路由到新版本；旧房完成后退出，避免在比赛中间强制换规则。服务升级前显示维护状态。自动重启能恢复进程，却不自动恢复局面；没有检查点恢复时应清楚记录中断并给玩家合理结果，而非宣传“零停机无损”。[W02]

# 18 同步、断线与迷雾安全
先发送最少必要的信息，再让画面平滑

现在采用服务端权威模拟，10Hz 向客户端发送按视野过滤的完整快照；渲染层已经做指数平滑。[S05、S08] 没有必要为了“RTS 常用锁步”贸然改成客户端确定性锁步。跨运行环境的完全确定性与防作弊成本需要单独论证。

| 模块 | 建议实现 |
| --- | --- |
| 增量状态 | 首次进入／恢复发送全量基线，后续按 baselineId、tick 发创建、变更、移除和必要事件；客户端确认基线，缺失时重同步。 |
| 可见性先行 | 先对每个玩家完成可见性、己方命令和记忆规则过滤，再做增量；绝不能先广播全图再由客户端隐藏。 |
| 精简数据 | 位置与朝向量化，去掉不需要的内部状态；迷雾压缩／差分；静态定义只按版本获取一次。 |
| 抖动处理 | 在已有平滑上增加带时间戳的快照缓冲；以约 150–250ms 为试验范围，并按延迟和抖动调节。 |
| 即时操作反馈 | 点击立即显示目标与命令状态；收到服务器 ACK 才确认执行。伤害、资源与胜负不做权威预测。 |
| 事件一致性 | 特效／提示带事件 ID，重连或基线恢复不得重复爆炸和播报；瞬移用明确事件，不插值穿越地图。 |

## 断线恢复规格

检测断线后锁定下令并显示倒计时。使用带抖动的 1／2／4／8 秒等重试退避，设置总重连窗口，例如 90 秒作为首版配置。服务端验证恢复令牌、房间、席位、协议和 buildHash，确认身份后发送新基线，客户端清空旧待播特效和失效选择。

命令携带单调序号；服务端保留已接受序号，重复命令只返回已有结果。只补发已知未确认且仍适用的命令，绝不把断线期间一串过时攻击指令无脑全部执行。现有恢复令牌能力只是基础，客户端自动化流程还需完成。

## 掉线期间采用明确房间规则

可选保持最后命令、短暂停顿或超时后 AI 接管；非竞技朋友房优先容错。选项必须全员可见，禁止恢复身份时同时出现两个操作者。公网管理房主离开不影响权威进程；服务端崩溃与玩家断网分开处理。

# 19 公网安全与运行保障
已有防护要保留，缺失的边界要补齐

服务器现有序号校验、命令权限、单连接频率限制、帧大小限制、心跳和写缓冲积压跳过发送，不应误写为“完全没有安全措施”。但代码也声明偏个人／LAN 使用，尚缺公网所需的会话边界、全局资源限制与运行隔离。[S08]

| 风险面 | 上线前要求 |
| --- | --- |
| 身份与恢复 | 创建、加入、恢复统一状态机；所有入口校验版本和会话归属；令牌过期／轮换，禁止出现在 URL、截图和普通日志。 |
| 连接与房间耗尽 | 每身份／IP 合理配额＋全局并发、房间、实体、内存和时间预算；考虑共享 NAT，不能仅凭同 IP 误封所有朋友。 |
| 协议输入 | 严格类型与范围、长度、数组上限、坐标与数值有限性；恶意消息只关闭对应连接，不拖垮所有房。 |
| 来源与跨站风险 | 公网使用允许来源名单和身份校验；LAN 与离线页面另设受控策略，不能直接沿用宽松 null 来源给公网。 |
| 慢客户端 | 增量合并、过期帧丢弃、发送队列上限和全量重同步；持续落后者断开并解释，不累积无界历史。 |
| 聊天与用户内容 | 频率限制、文本转义、静音／屏蔽、举报与处理流程；名称长度和字符规则；不将输入直接拼入 HTML。 |
| 可观测性 | 分离 RTT、模拟 tick 耗时、序列化耗时、帧率、内存和每房带宽；报警能指明是客户端还是服务端。 |
| 运维与发布 | 自动证书续期、健康检查、异常重启、容量上限、维护公告、滚动停收新房和回滚版本。 |

## 上线合规与资产台账

中国大陆服务器提供网站／APP 服务时，需按实际业务完成相应备案和接入流程；腾讯云官方提供此类要求说明。[W05] 游戏公开运营、隐私、未成年人保护和权利授权是否还有其他要求，应由具备资质的运营方具体核查。ICP备案并不等于全部游戏运营手续或知识产权许可。

日志默认不记录命令中的凭据和完整聊天隐私；明确保存周期、导出诊断内容及用户告知。成本、投诉处理、备份、密钥管理与停服安排需要明确责任人。没有这些责任归属，“公用服务器永久可连”就不是可靠的交付承诺。

# 20 性能、容量与费用判断
本次数据是基准样本，不是公网容量承诺

本次在 Node v22.16.0、Intel Xeon Platinum 8573C 环境运行合成场景：八个归属的坦克密集战斗，保持单位数量，100 个模拟步，共 10 秒模拟时间。下表不含 GPU、真实网络传输和大规模多房运行。[T04]

| 单位数 | 平均每步 ms | p95 每步 ms | 单份快照字节 |
| --- | --- | --- | --- |
| 100 | 1.169 | 4.294 | 54,489 |
| 300 | 1.654 | 3.112 | 142,918 |
| 600 | 2.085 | 3.303 | 275,762 |

## 需要优先控制的是发送体积

以 600 单位样本计算，275,762 字节 × 10 次／秒 ≈ 2.76 MB／秒，即约 22.06 Mbit／秒／客户端。若八个接收者都收到同等大小快照，一房约 176.49 Mbit／秒原始载荷。这是条件性算术推算，不是实际线速实测；真实视野、状态大小和传输开销会改变结果。

因此应先做增量、量化、静态数据分离和迷雾压缩，再据真实场景选择云资源。模拟代码运行快，不代表完整服务器吞吐高；每个客户端分别过滤和序列化，也会占用 CPU。

## 建议预算与验收目标

首轮目标可设：300 个可见单位的持续对局，单客户端平均下行载荷不超过 50 kB／秒，p95 不超过 100 kB／秒；首次全量加载和恢复单独统计。这只是工程目标，须由真实运动密度、事件和视野规模验证；不达标时先解释原因，不以丢失状态换数字。

10Hz 模拟的每步预算是 100ms。正式容量下建议整个房间循环 p95 小于 50ms、p99 小于 80ms，并有余量；指标包含模拟、过滤、序列化与发送调度。渲染分别测 1080p、300／600 单位、各种效果与 1366×768 UI；不能用服务器 CPU 数据证明 60 FPS。

## 费用按实际模型核算

月成本 = 计算资源＋公网带宽／流量＋存储与备份＋日志监控＋域名／证书相关支出＋运行维护。请求云厂商正式报价时再填写金额，不把促销首月价或开发免费额度宣传成长期免费。设置费用提醒和容量硬上限，满载时优雅排队／拒绝开房。

## 工作并行方式

玩法线负责规则、地图、AI与验证；体验线负责 UI／操作／新手引导；网络线负责会话、同步和运行；美术线按样板与资源清单迭代。跨线依赖先定义协议与数据结构，避免把 UI 逻辑直接写进模拟核心。

关键依赖：公平开局先于对战平衡评价；版本／规则标识先于公网匹配；状态完整先于增量压缩与回放；完整特效事件先于网络表现；样板规格先于大量制作资产。各线可以并行，但这些依赖不能跳过。

## 这一轮暂缓

完整战役、海量新国家、排位赛季、商业化成长、复杂社交系统，以及未经样板验证的大规模引擎迁移。它们会增加工作量，却不直接解决当前“能否公平开局、看懂操作、稳定和朋友联机”的核心问题。

> 本表是开发顺序与完成条件，不是已完成内容，也不是工期承诺。原作机制逐项验证、完整美术和公网运营是不同工种；应在确定团队与资源后再估算人周和日历时间。

## 不能把“非商业”直接等同于公开授权

EA 的 C&C 专项 Mod 政策允许符合条件的非商业 Mod，并规定标识、宣传和资产使用边界，明确不能在 Mod 中包含 C&C 游戏音乐文件；一般内容政策对同人游戏等另有约束。此独立网页项目是否属于专项政策适用范围，不能仅凭名称或自制模型断定，应在公开上线前确认。[W06、W07]

建议先完成原创资产与来源清单，避免暗示官方产品或官方服务器。服务器存在不等于得到作品授权；ICP备案也不代替知识产权或游戏运营事项核查。上述内容是发布风险识别，不是对具体项目已获许可或必然侵权的法律结论。
