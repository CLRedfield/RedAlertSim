# 网页版三维《红色警戒2：尤里的复仇》开发规格

版本：0.1  
日期：2026-09-05  
状态：已确认产品方向，技术方案和验收方案待实现与测试。本文档不是可运行游戏，也不代表任何系统已经完成。

## 1. 用户已确认的方向

| 项目 | 已确认要求 |
| --- | --- |
| 规则 | 1A：规则、数值、操作尽量忠实原版，不自行重做平衡 |
| 美术 | 2A：保留红警2轮廓与比例的精细风格化三维 |
| 模式 | 3C：单机和联机同时作为首要目标 |
| 内容边界 | 4A：全单位与机制覆盖遭遇战和沙盒，本阶段不复刻完整战役 |
| 目标设备 | RTX 4060；CPU、内存、显卡桌面/笔记本型号尚未提供 |
| 玩家规模 | 最多8个参战席位，允许真人与AI混合 |
| 用途 | 用户自己玩，不按商业发行项目规划 |

项目目标：表现层三维化，规则层保持原版兼容。不能用模型数量代替机制完成度，不能把测试用简化原型称作完整重制版。

## 2. 原版规则基线

建议锁定《尤里的复仇》1.001，使用未安装玩法模组的基准内容。原版《红警2》与资料片的不同单位归属和规则，不应简单叠加。不引入《共和国之辉》《心灵终结》或社区重平衡作为默认规则。

### 2.1 核对优先级

1. 用户合法持有的干净基准版本的规则数据，以及该版本实际运行结果。
2. 原版手册、原始补丁说明与能够定位出处的资料。
3. 尚未完成对照的实现必须显式标注，不凭记忆填写后标为已还原。

规则数据的导入不等于原引擎行为已经复现。寻路、弹道、目标获取、AI、特殊能力和事件顺序仍需对照测试。

### 2.2 不擅自现代化的项目

- 单位价格、生产时间、血量、装甲、武器、攻击间隔、射程与升级。
- 科技前置、国家专属、生产规则、电力影响、建筑放置与占地。
- 经典鼠标操作、选择逻辑、编队与默认快捷键。
- 地图黑幕、侦测、雷达和已探明区域的显示规则。
- AI与难度修正：以基准版本为核对目标，不能擅自改为新设计后仍称原版。
- 原版已有、影响对战的特殊互动：逐项判断并记录，不私自删除。

界面缩放、分辨率、材质质量和纯表现选项可以适配现代设备。崩溃、卡死、越权和网络安全问题不作为复刻目标。影响玩法的兼容性差异须记录并可追溯。

## 3. 完整内容的定义

### 3.1 势力与科技树

包含盟军、苏军、尤里三套主要科技体系，以及美国、英国、法国、德国、韩国、苏俄、伊拉克、古巴、利比亚和尤里，共十个可选势力。每项数据仍需与基准版本逐项核对。

### 3.2 内容分层

| 内容 | 范围 | 出现方式 |
| --- | --- | --- |
| 常规单位与建筑 | 三体系完整遭遇战生产内容 | 正常科技树 |
| 国家特色 | 专属单位、建筑与支援能力 | 对应国家解锁 |
| 条件与组合内容 | 特殊科技解锁、驻兵/载具组合、派生攻击单位等 | 原版条件触发 |
| 地图中立内容 | 中立建筑、可交互设施与环境对象 | 地图设置 |
| 战役/地图专属单位 | 原版实际存在的特殊单位 | 沙盒与脚本接口，不强行加入普通生产栏 |

原版遗留但未启用的内部对象，应登记为“未启用/待核实”，不自动变成正式玩法内容。正式单位数在完成类型表、别名、变体和生成物去重后公布。

### 3.3 每个对象的完成状态

每个单位/建筑须记录：内部ID、中文名、所属体系、可用国家、生产前置、经济与战斗数值、能力、模型、动画、图标、音效来源、AI支持、联网测试、已知差异。

完成度分别记录：已登记、可生产/生成、机制可运行、原版对照通过、美术完成、AI验证通过、联网验证通过。禁止以统一“已完成”掩盖缺项。

## 4. 玩法与模式

### 4.1 遭遇战

最多8个参战席位，席位可为真人、AI或关闭；支持1人+7AI、多人合作对AI、团队对战和自由混战。房间保存国家、颜色、队伍、出生点和基准规则选项。规则选项的默认值需从基准版本核对，而非临时拍定。

需要完整开局至结算流程：部署基地、经济循环、建造、侦察、生产、交战、胜负判定、结算。退出与掉线行为必须明确，不能擅自让AI接管被当作原版行为。

### 4.2 沙盒

用于全单位展示与机制验证。提供生成双方单位、设置科技、重置资源、调整单位等级、测试地图对象等工具。沙盒修改命令与正式对战严格区分，普通客户端不能把沙盒命令发给对战服务器获得资源。

### 4.3 存档与回放

单机存档需要保存规则版本、地图、实体、生产队列、控制关系、AI状态和随机状态。回放保存基准版本、初始状态与指令/事件记录，并进行可重复性验证。多人重连属于网络恢复，不等同于任意加入已经开打的比赛。

## 5. 三维表现与界面规范

### 5.1 镜头与逻辑

默认采用贴近原版指挥视角的固定斜俯视镜头，优先正交投影。缩放范围要兼顾辨识度和信息量。正式对战不把自由绕视、近距离跟拍和摄影模式作为默认功能。

视觉模型与规则碰撞体分离。逻辑格、占地、通行、攻击判定与原版核对，不用真实物理碰撞直接替代。三维动画不能改变生产、攻击或位移的实际结算时机。

### 5.2 资产质量要求

- 车辆需要可区分的车体、炮塔与炮管，处理转向、开火后坐和受损状态。
- 建筑需要完整轮廓、关键运行部件、建造/受损表现与阵营色。
- 步兵需要清晰剪影、正确武器与基础状态动画，不以圆柱体作为最终模型。
- 空军、水面与水下单位需要对应的状态和移动表现。
- 地形材质、道路、海岸、植被、残骸和特效采用统一尺度与风格。
- 正式可玩资产不能以拼接不同风格素材包作为美术完成标准。

先用代表性车辆、建筑、步兵、地形和侧栏确定质量基准。临时占位资产只允许用于明确标记的工程测试。

### 5.3 UI要求

保留原版右侧生产栏的结构、信息层级与操作习惯。按盟军、苏军、尤里基准侧栏重绘高清视觉，不重新设计为完全不同的科幻控制台。

包括主菜单、单机设置、联机房间、载入、战斗HUD、暂停/设置、结算、沙盒与图鉴。战斗HUD覆盖资金、电力、雷达、生产类别、生产状态、维修、出售、部署与必要提示。

默认简体中文。可调界面缩放、音量与画质。对尚未有可用音频的提示，允许临时文本或原创占位音效，但须标记，不称已还原配音。

## 6. 技术架构建议

以下是待实现的架构决策，不是已实现功能。

### 6.1 客户端

TypeScript + Babylon.js，WebGL 2作为首轮基线，WebGPU作为后续可选渲染路径。UI使用HTML/CSS。发布包固定依赖版本，不能依赖未经锁定的线上“最新版”脚本。

画面可以平滑插值，但战斗逻辑按固定步长推进。不能将屏幕帧数直接当作攻击、生产或移动速度。具体逻辑频率与速度档映射须由基准对照确定，不能武断指定频率后声称忠实。

### 6.2 共享模拟核心

同一份无渲染依赖的规则代码负责经济、生产、移动、战斗、能力、AI与胜负。

单机：在浏览器Web Worker中运行模拟，UI与渲染留在主线程。

联机：在Node.js房间进程中运行同一模拟核心，作为权威状态。客户端提交指令，不提交任意资金、伤害或位置结果。服务器验证指令与视野相关权限，输出初始快照、状态增量和必要校正。

采用统一随机种子、稳定处理顺序、状态序列化和版本散列，为保存、重连和回放提供基础。这里选择服务端权威，不把它混称为全客户端确定性锁步。

### 6.3 网络

WebSocket作为首轮传输方案。房间建立、准备、地图/规则版本校验、开局、指令、断线、重连和结束都需要协议状态机。

本机测试：多浏览器连接本地房间进程。

局域网：房间服务在局域网内可访问。

异地：所有玩家必须能访问同一个服务端地址。房间码只标识房间，不会自动解决网络连通。交付可包含服务器源码与部署说明，不宣称已经提供永久公共服务器。

网络模拟测试覆盖延迟、抖动、断线和重复提交指令。WebSocket使用可靠有序传输，网络丢包带来的延迟与重连问题仍须测试。

### 6.4 数据与模块

建议分离客户端、共享规则、服务端、内容清单、模型音频资源、测试与文档。AI必须通过与玩家兼容的指令路径影响游戏，特殊规则例外须明确配置和记录。

## 7. 核心机制验收矩阵

下表是需要对照基准行为的测试项目，并不预先断言所有细节的实现方式。

| 系统 | 关键验证 |
| --- | --- |
| 经济 | 采矿、运输、卸矿、矿区耗尽、采矿设施被毁或被控 |
| 生产与电力 | 前置建筑、低电力、队列、暂停/取消、建筑出售与生产中断 |
| 运动与寻路 | 陆地、两栖、水面、水下、空中、桥梁与障碍变化 |
| 运输与驻兵 | 容量、上下客、载具组合、被毁后的乘员处理 |
| 心灵控制 | 目标合法性、所有权变化、控制者死亡、过载、连锁关系 |
| 部署与变形 | 部署条件、可通行/可放置位置、武器与状态转换 |
| 特殊攻击 | 抬升/牵引、持续区域伤害、特殊建筑作用与状态解除 |
| 情报 | 黑幕、雷达、隐蔽、侦测、伪装与客户端可见信息 |
| 科技解锁 | 特定入侵/占领/国家条件、科技失去后的行为 |
| 超级武器 | 解锁、电力依赖、计时、目标合法性、持续与结束 |
| AI | 经济扩张、生产、目标选择、特殊能力、难度规则 |
| 存档/联网 | 复杂状态保存恢复、两端一致、重连、版本不匹配拒绝 |

每项记录基准版本、场景、步骤、预期结果、实际结果、已知差异和测试日期。不能只对照数值，不对照行为。

## 8. 性能与可靠性目标

RTX 4060是用户给出的目标显卡，不代表已经测得性能。CPU、内存和显卡具体形态未知，必须纳入实测报告。

建议首轮显示目标：1920×1080，高画质，通常战局争取60 FPS。该数值是工程目标，不是承诺或测试结果。

压测依次覆盖8方、100/300/600个活动作战单位以及独立记录的建筑、投射物与特效负载。压力档是测试规模，不是额外加给游戏的人口上限。1440p作为扩展测试，不先承诺固定帧率。

记录平均帧率、慢帧、模拟步耗时、内存、网络流量及连续对局稳定性。优化优先处理寻路预算、目标搜索、视野计算、批量渲染、细节层级和效果数量，不能用偷偷减少单位或禁用能力来冒充完整兼容。

## 9. 阶段交付与验收门槛

### M0：规则与美术基准

输出基准清单、十势力内容登记、机制矩阵、代表性模型与侧栏规范。未核实数据明确标注。

### M1：首个可玩的单机/联机纵向切片

范围：三体系的代表性经济、生产与战斗链；一张8出生点测试地图；双端真实联机；AI基础完整对局；至少一套尤里特殊机制的端到端测试；达到风格基准的代表性资产。

门槛：能从开局玩到结算；两端的关键状态一致；单机与联机使用同一规则核心；提供实际测试记录。此阶段不是全单位最终版本。

### M2：全内容与复杂交互

补齐全部势力、单位、建筑、海空军、条件解锁、组合机制和超级武器。补全复杂AI行为、联网状态与基准对照。新增海岸/水域、城市与桥梁等机制测试地图。每项有清单可核对。

### M3：整合交付

完成统一美术、UI、设置、存档/恢复、回放基础与部署说明；进行8方长局、混合真人/AI及不同网络条件测试。公网测试与本机多窗口测试分别报告。

### 最终包目标结构

- 可运行网页构建与资源。
- 客户端、共享模拟核心、服务端完整源码。
- 本地启动入口与依赖说明。
- 联机房间服务与部署说明。
- 内容完成表、原版差异表、机制测试表、性能实测报告。
- 美术/音频资源来源与许可记录。
- 已知问题和后续开发任务。

这些是交付目标，不表示这些目录或代码已经创建。

## 10. 资源、用途与授权边界

本项目用途按个人使用规划，不包含账号体系、商业化、付费内容或公共排行榜。

个人使用不是自动获得官方授权。EA公开内容政策并未给予本项目授权，并明确对同人游戏、游戏复活项目、原始资源分发等设有限制。自行重建三维模型也不能简单等同于不存在其他权利问题。

工程不默认捆绑来自不明下载站的原版音乐、配音、界面素材或完整安装资源。可设计用户本地资源导入接口，但导入不等于已解决所有授权问题。任何未来的分享或公开上线需要另行检查适用授权和法律问题。

不要求用户提交账号、密钥或完整安装包。精确规则核对需要时，再确认用户是否持有未安装模组的基准版本及可提供的规则资料。
